HTTP: qué ocurre al solicitar una página

Cuando abres una página, el navegador envía una solicitud y recibe una respuesta del servidor. Vamos a leer juntos el método, el código de estado, las cabeceras y el contenido con una terminal simulada de RINXI.

De una dirección a una respuesta

Al solicitar una URL, el navegador identifica el servidor y el recurso que quiere. Antes del intercambio HTTP pueden intervenir DNS y una conexión de red; si la dirección usa HTTPS, también se establece la protección TLS. Esta práctica se concentra en los mensajes HTTP que describen la solicitud y la respuesta.

1

El cliente solicita
El navegador envía un método, un recurso y cabeceras que aportan contexto.

2

El servidor responde
Devuelve una línea de estado y cabeceras; puede incluir el contenido solicitado.

3

El navegador interpreta
Usa el código y las cabeceras para decidir cómo tratar la respuesta y representar el contenido.

Una solicitud GET sencilla

El comando de ejemplo del ejercicio es curl -i http://aula.rinxi.test/. La opción -i pide a curl que muestre las cabeceras de respuesta junto con el contenido. Una solicitud GET intenta obtener la representación del recurso indicado.

Forma simplificada de la solicitud:
GET / HTTP/1.1
Host: aula.rinxi.test
User-Agent: curl (simulado)
Accept: */*

La primera línea identifica el método, la ruta del recurso y la versión del protocolo. Las cabeceras aportan datos adicionales para procesar la petición.

Cómo leer la respuesta

ParteEjemploQué indica
Línea de estadoHTTP/1.1 200 OKVersión y resultado general
CabeceraContent-Type: text/htmlFormato del contenido
SeparadorLínea vacíaTermina las cabeceras
ContenidoHTML de la páginaRepresentación que puede mostrar el navegador

El código 200 significa que la solicitud tuvo éxito. Si el recurso no existe en este servidor ficticio, recibirás 404 Not Found. La respuesta 404 también es una respuesta HTTP válida: informa de que no se encontró ese recurso.

Otros códigos comunes: 301 indica una redirección; 500, un error interno del servidor. El código no explica por sí solo toda la causa, así que también se leen las cabeceras y el contenido.

Tu objetivo en este ejercicio

Solicita la página de bienvenida. Identifica el código de estado, el tipo de contenido y el texto HTML que recibe el cliente. Después pide una ruta inexistente y compara la respuesta.

Objetivo esperado: la portada responde 200 OK con HTML; /no-existe responde 404 Not Found.

Cómo probarlo

Escribe curl -i http://aula.rinxi.test/ en la terminal. Lee la línea que empieza por HTTP/1.1, localiza Content-Type y revisa el contenido que aparece después de la línea vacía. Luego prueba curl -i http://aula.rinxi.test/no-existe.

Puedes abrir los botones de ejemplo, escribir pista o consultar help.

Esta terminal es completamente simulada. No ejecuta curl, no resuelve el dominio, no abre conexiones ni descarga una página. Ambas respuestas están preparadas para el ejercicio y se muestran únicamente en esta página.

Fuentes y alcance

La sintaxis de HTTP/1.1 separa la línea de estado, las cabeceras y el contenido. HTTP define códigos como 200 y 404 y cabeceras de representación como Content-Type. Consulta RFC 9112 · HTTP/1.1 y RFC 9110 · HTTP Semantics. El sufijo .test está reservado para pruebas, según RFC 6761.
